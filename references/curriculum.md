# 七阶段 Skill 创建课程

这门课的目标不是“知道 Skill 是什么”，而是完成一个能被 Codex 正确发现、执行和验证的 Skill。默认每阶段 10–30 分钟，一次只做一个练习。

## 阶段 1：判断是否真的需要 Skill

**学习目标**：区分一次性提示词、项目说明和可复用 Skill。

**讲解要点**

- 一次性任务：直接在对话里说明即可。
- 项目约定：优先放在 `AGENTS.md`、README 或项目配置中。
- 可复用能力：需要在多个任务中改变 Codex 的判断或动作，才适合做成 Skill。

**练习**

用一句话回答：

> 我希望 Codex 在什么场景下，反复做出什么与默认行为不同的动作？

如果不能同时说清“场景”和“不同动作”，先不要创建 Skill。

**产出**：一句通过检查的需求陈述。

**通过标准**：包含目标用户、触发场景、期望动作和可观察结果。

## 阶段 2：定义一句话目标和成功标准

**学习目标**：把“我想做个好用的 Skill”变成可验收的行为。

**模板**

> 当用户需要【任务】时，Codex 应该【关键动作】，最终产出【可观察结果】；不适用于【边界】。

**练习**

为一个“自动整理会议纪要”的 Skill 写目标和成功标准：

- 输入是什么？
- 必须产出什么？
- 哪些内容不能编造？
- 什么情况下不应该触发？

**产出**：目标句 + 三条成功标准 + 一条排除边界。

**通过标准**：换一个人阅读后，能判断结果是否完成。

## 阶段 3：命名与 description

**学习目标**：让 Skill 在正确的请求中被发现，而不是吸引所有请求。

**规则**

- 名称使用 lowercase-hyphen-case，和目录同名。
- `description` 先写能力，再写适用场景，最后写必要边界。
- 不写“万能”“任何任务”“最强”等无法路由的词。
- 不把完整工作流塞进 description。

**练习**

写一个不超过 500 字符的 description，然后检查：

1. 用户会自然说出哪些触发词？
2. 哪些相似任务不应触发？
3. 仅看描述，能否判断正文大概提供什么？

**产出**：名称 + description 草稿。

**通过标准**：至少能举出两个应该触发的请求和一个不应触发的请求。

## 阶段 4：最小可用 SKILL.md

**学习目标**：写出一个短小、可执行、能完成单一路径的 Skill。

**最小结构**

```markdown
---
name: example-skill
description: 一句话说明能力和适用场景。
---

# Example Skill

## 目标

## 工作流

## 约束

## 验证
```

**练习**

复制 `assets/minimal-skill-template/`，只完成一个主路径。暂时不要添加脚本、参考资料或复杂分支。

**产出**：最小 `SKILL.md`。

**通过标准**：没有 TODO；每一步都能被另一个 Codex 实例执行；包含明确的完成条件。

## 阶段 5：补充分支、约束与条件资源

**学习目标**：只在真实分支需要时增加复杂度。

**判断表**

| 现象 | 处理 |
|---|---|
| 某段说明只在少数模式使用 | 移到 `references/` |
| 同一逻辑会被反复重写 | 写成 `scripts/` |
| 输出需要固定模板或素材 | 放入 `assets/` |
| 普通能力已经足够 | 不增加任何结构 |

**练习**

列出两个真实失败场景，并为每个场景增加一个条件规则。不要为了“完整”预填所有可能情况。

**产出**：条件分支、停止条件、失败处理和必要资源入口。

**通过标准**：每条复杂规则都有真实任务依据；没有未使用的目录或占位文件。

## 阶段 6：结构验证与真实任务测试

**学习目标**：用证据而不是自我感觉判断 Skill 是否可用。

**结构验证**

```bash
python scripts/validate_skill.py <skill-directory>
```

**前向测试**

准备三个真实请求：

1. 一个典型成功场景。
2. 一个容易误触发的相邻场景。
3. 一个信息不足或需要停止的场景。

让不了解预期答案的执行者使用 Skill，检查它是否：

- 在正确场景触发。
- 按工作流完成任务。
- 不越过授权边界。
- 在信息不足时停下来。
- 产出可验证的结果。

**产出**：验证结果 + 至少一个由测试暴露出的修复。

**通过标准**：结构检查通过；三个测试至少覆盖触发、执行和边界；修复有实际证据。

## 阶段 7：打包、发布和升级

**学习目标**：让陌生人可以安装、理解、验证和反馈。

**硬性结构与推荐实践**

硬性结构基线：

- 根目录存在 `SKILL.md`，frontmatter 至少包含 `name` 和 `description`。
- 名称和目录一致，描述能路由到正确场景。

推荐发布实践（不是所有运行时的官方强制要求）：

- `agents/openai.yaml` 提供 UI 元数据。
- README 包含用途、安装、快速开始、示例、限制和许可证。
- 版本号写入 metadata 和 CHANGELOG。
- 使用 MIT License，并保留第三方方法论归属。
- GitHub Actions 运行结构验证、单元测试和链接检查。
- 在干净环境中安装并完成一次真实任务。
- 创建 `vX.Y.Z` 标签和 GitHub Release。

向用户解释时，必须区分“结构硬性要求”和“本项目推荐实践”。

**产出**：可安装的 GitHub 仓库和首个 Release。

**通过标准**：新用户只读 README 就能安装；Release 说明包含示例、变更和已知限制。

## 教练提问模板

当用户卡住时，优先问这三类问题：

1. **场景**：你希望它在什么时候触发？
2. **动作**：Codex 默认会怎么做，你希望它改成什么？
3. **证据**：什么结果能证明这次改动有效？

不要连续问超过两个问题。能给出安全默认值时，先给默认值再让用户调整。
